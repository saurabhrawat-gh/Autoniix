# Research Agent Workflow

The Research Agent runs before any Dev work begins. Its job is to read the issue spec and understand the codebase deeply enough to give the Dev Team a precise, risk-free implementation path.

**Usage:**
```
/research-agent #N       — run for a specific issue
/research-agent          — run for the highest-priority ready-for-dev issue
```

---

## Team Structure

- **Research Lead** — orchestrates the three sub-agents, writes the final `research_notes` comment
- **Codebase Analyst** — maps which files/functions/tables are affected and how
- **Dep Auditor** — scans `requirements.txt`, `package.json`, and Docker images for conflicts or missing packages
- **Architecture Advisor** — recommends the cleanest implementation approach consistent with existing patterns

---

## Step 1 — Research Lead: Orient

1. Call `mcp0_get_issue` to read the full issue body
2. Extract: Summary, Use Cases, Acceptance Criteria, Impacted Files section
3. Note the issue title format: `[Type] | [Layer] | Description` — understand which layer is primary
4. Check if a test-case issue already exists (linked in issue body as `**Test Plan:** #{N}`)
5. Print: "Research starting for #N: {title}"

---

## Step 2 — Codebase Analyst: Impact Map

Scan the codebase for every file that will need to change.

For each item in the Impacted Files section of the issue:
1. Read the file using the read file tool
2. Find the relevant function/class/route
3. Identify: what changes, what callers/dependents exist, what tests exist

Also search for:
- Any existing similar implementation (to reuse patterns, not reinvent)
- Any existing test files for the impacted modules
- DB migration files if schema changes are required
- API contract files if endpoints are modified

Output from Codebase Analyst:
```markdown
### Codebase Impact

| File | Change Type | Risk |
|---|---|---|
| src/api/webhooks.py | New endpoint | medium |
| src/db.py | New table column | high |
| tests/test_webhooks.py | New test file | low |

**Existing patterns to follow:**
- Authentication middleware: see `src/gateway/auth_middleware.py:L45`
- DB migration style: see `scripts/migrations/202605170001_auth_cookies.sql`
- Test fixtures: see `tests/fixtures/llm/`
```

---

## Step 3 — Dep Auditor: Dependency Check

Check for any new packages or version conflicts.

1. Read `requirements.txt` and `dashboard/package.json`
2. Cross-check against any new packages mentioned in the issue spec
3. Check for known conflicts (e.g., pinned versions that clash with new deps)
4. Check Dockerfiles for base image compatibility

Output from Dep Auditor:
```markdown
### Dependencies

| Package | Action | Notes |
|---|---|---|
| httpx | already installed (0.27.0) | no change |
| slack-sdk | needs adding | `pip install slack-sdk==3.33.0` |

**Dockerfile:** No changes needed.
```

---

## Step 4 — Architecture Advisor: Recommended Approach

Based on the issue spec and Codebase Analyst findings, recommend the implementation approach.

Rules:
- Always follow existing patterns (provider pattern, gateway structure, etc.)
- Never recommend a new architectural pattern unless the existing one genuinely cannot handle the spec
- If multiple approaches exist: list them with trade-offs, then recommend one
- Scope is strictly within what the issue spec says — do not suggest additional scope

Output from Architecture Advisor:
```markdown
### Recommended Approach

**Primary approach:** {1-2 sentences on what to build and where}

**Key decisions:**
- {Decision 1}: {rationale}
- {Decision 2}: {rationale}

**Avoid:**
- {Anti-pattern or trap to skip}

**Estimated complexity:** {S (< 2h) / M (2–8h) / L (1–2d) / XL (> 2d)}
**DB migration required:** {yes/no}
**GHA changes required:** {yes/no}
```

---

## Step 5 — Research Lead: Assemble and Post

Compile all three sub-agent outputs into a single comment on the issue.

Call `mcp0_add_issue_comment` with:

```markdown
## Research Notes

> Generated by Research Agent before implementation. Dev Team reads this before writing any code.

### Codebase Impact
{Codebase Analyst output}

### Dependencies
{Dep Auditor output}

### Recommended Approach
{Architecture Advisor output}

---
*Research complete. Awaiting conductor checkpoint before Dev Team picks up.*
```

---

## Step 6 — Emit HandoffPayload

```yaml
handoff:
  from_team: research
  to_team: qa          # Mode A — test plan
  issue: {N}
  summary: "Impact map complete. {N_files} files identified. Approach recommended."
  risk_level: {from Architecture Advisor}
  actions_pending:
    - "QA Agent Mode A generates test plan"
    - "Dev Team reads research_notes before implementation"
  blockers: []
```

---

## Rules

- Never write or suggest code — only analysis and recommendations
- Never change issue labels or status
- Do not expand scope beyond what the issue spec says
- If the issue spec is incomplete (missing Impacted Files, missing ACs), flag it in the notes and ask the conductor to route back to BA
- Research notes are comments on the issue — they survive session restarts
